An all-in-one training app for vertical jump, athleticism, and upper body

Nutrition, an exercise directory, workout generation, and progress tracking in one app that knows your history, your current state, and your preferences, and gets better at programming for you the longer you use it.

Where things stand today

No application code

The repo holds AGENTS.md (symlinked as CLAUDE.md) and thp.pdf. Nothing else. Every technical choice below is open rather than inherited.

A real domain reference exists

The condensed ebook distillation gives concrete, machine-checkable prescriptions: set and rep ranges, rest windows, weekly frequencies, the rule of 60 percent, and a four-phase tendon protocol.

The domain fights naive tracking

Vertical jump is supposed to drop mid-block. Each capacity has its own fatigue curve. Plyometrics can make some athletes jump lower. This shapes the whole design.

The load-bearing decision

Claude proposes. A rule engine decides what ships.

The obvious build is "ask a model for today's workout." That fails here for a specific reason: one-foot jumping loads a single leg at up to fourteen times bodyweight, and the ebook says plyometrics are the easiest thing to get wrong badly enough to make an athlete jump lower. A model that drifts on plyometric dosage does not produce a slightly worse workout. It produces a tendon injury that costs months.

So the ebook's prescriptions become executable rules in plain TypeScript. But you raised the right objection: a single gate with seventeen pass/fail rules in front of it would reject constantly. So the rules are not all enforced the same way. Most of them are arranged so that there is nothing left to fail.

Why it will not fail constantly: mesocycle rules run when a block is declared and again when a week is generated, never per session, so an individual day can only trip session-scope rules and almost all of those are normalized rather than checked. Thresholds are bands with slack, not exact numbers.
And it is measurable before it matters: the engine is built and unit-tested before any generation code exists, so phase 5 logs the repair-attempt distribution over about fifty generations. If the first-attempt pass rate is under 80 percent, the fix is the prompt or the normalizer, not more rules.

pre-filter

The option is deleted from the candidate set before the prompt is built. The model cannot pick it, so the rule cannot be broken and never triggers a repair.

normalize

There is exactly one correct answer, so code computes it. The model supplies exercise selection and intent; the engine sorts, clamps, and labels. The diff is shown to you.

block

Genuine structural judgment that code cannot fix without rewriting the plan. Triggers the repair loop. Four of the five are mesocycle or microcycle scope, so they run at block declaration and weekly generation, not per session.

advisory

Attached to the proposal as a note and to the memory layer as a signal. Never blocks. If the same advisory keeps firing and you keep accepting, that is information about you, not an error.

Progress tracking that does not lie to you

This is a genuinely unusual requirement and worth calling out. The ebook says vertical jump should drop during hard accumulation work, and that backing off at planned times is what produces supercompensation. A plain line chart of vertical over time would therefore encourage exactly the wrong reaction to a normal, healthy training response.

Depth jump calibration

Implements the ebook protocol directly: test standing vertical, raise box height until measured vertical drops below it, record the matched height as a derived insight the generator then uses.

Pain against contact volume

Tendon pain plotted against weekly high-impact ground contacts. This correlation is the main early warning signal you get before something becomes reactive tendinopathy.

Relative strength trend

Key lifts divided by bodyweight, not absolute load, because relative strength is what the ebook ties to jumping. Absolute numbers get secondary billing.

Prescription calibration

Logged RPE and completion against what was prescribed. If generated plans run consistently too hard or too easy, this is where it shows up.

Data model

The exercise directory is the part worth dwelling on. It encodes the ebook's own taxonomy rather than generic gym metadata, because those attributes are precisely what the generator needs in order to reason instead of pattern-match on exercise names.

Exercise directory

Per exercise: muscle group, movement pattern, position on the force velocity curve, equipment, unilateral or bilateral, plane of motion, coupling time class for plyos, tendon load rating, coaching cues, progression and regression links, and a technical complexity score used for session ordering.

Athlete state

Profile including dominant takeoff leg, jumper type, and arm swing style, since the ebook says not to switch a trained jumper's strategy. Plus measurement time series, per-site tendon status with protocol phase, and readiness check-ins.

Proposals and verdicts

Every generated plan is stored with its rationale, the exact inputs it saw, the validator report, and your verdict with a reason. This is both the audit trail and the primary signal the memory layer learns from.

Memory and insights

Typed facts with embeddings, a source distinguishing what you said from what was inferred, confidence, and a supersedes pointer so corrections replace rather than pile up. Separately, derived insights computed by analytics rather than asserted by a model.

Tendon tracking caveat, straight from the source: structure does not equal pain. Some athletes have severely degenerated tendons and no pain, others the reverse. So the schema tracks function and pain only, and no screen ever implies structural damage.

How it gets smarter

"AI-forward" only means something if knowledge accumulates. Three separate mechanisms, and they are worth keeping distinct because they have different failure modes.

1

Stated preferences

Things you tell it directly. Highest confidence, never overwritten by inference. Retrieved into the cached context prefix on every generation.

2

Inferred patterns

A reflection job reads each logged session against what was prescribed, plus your notes, and proposes memory writes. Low-risk facts auto-commit. Anything that would change future programming asks first.

3

Computed insights

Analytics, not model output. Your calibrated depth jump height. The weekly contact count above which patellar pain rises. Your actual rate of strength progression per block type.

Data source

WHOOP is the objective input layer

This replaces the Apple Health route, and it is a straight upgrade. WHOOP exposes a real server-to-server API with OAuth and webhooks, so there is no third-party export app in the path and no phone that has to be awake for data to arrive. It also gives higher-quality inputs than HealthKit would have: recovery score, HRV as rmssd, resting heart rate, sleep stage composition, and day strain, all already normalised against your own baseline by WHOOP.

Connection

OAuth 2.0 authorization code flow against api.prod.whoop.com/oauth/oauth2/auth and /token, with scopes read:recovery, read:cycles, read:sleep, read:workout, read:body_measurement, and offline. Access tokens last an hour, and refreshing rotates the refresh token and invalidates the old access token, so the pair is stored in one row and replaced in one transaction. Since the app is single-user, this connects once and then lives as a server-side background job.

Ingest

Webhooks at /api/whoop/webhook for sleep.updated, recovery.updated, and workout.updated plus their deletes, verified as base64(HMAC-SHA256(timestamp + rawBody, clientSecret)) against the X-WHOOP-Signature header with a timestamp freshness window. The payload carries only an id and type, so each event triggers a fetch of that record from the v2 API. Day strain and body measurements have no webhook, so a nightly job pages the cycle collection. Collections cap at 25 records per page with nextToken, so backfill is paginated and rate-limit aware.

What it does and does not cover

Covered: recovery score, hrv_rmssd_milli, resting_heart_rate, SpO2, skin temperature, sleep stage summary and performance percentage, day strain and kilojoules, and per-workout strain and heart-rate zones. Not covered: vertical jump, tendon pain, RPE, and load lifted, which stay manual, and daily bodyweight, since WHOOP treats weight as a profile field rather than a measurement series. Every row lands in measurements with source = "whoop", so a manual entry and a device reading are never confused, and raw payloads are kept so a schema change is replayable rather than lossy.

Why this matters for generation: readiness stops being a questionnaire you have to remember to fill in. WHOOP recovery, sleep, and strain are already there each morning, so the pre-session risk score and the load decision have real objective input from day one rather than after eight weeks of diligent self-reporting. The check-in shrinks to what only you know: soreness, motivation, and tendon pain.

Statistical and ML insights we could compute

A full menu, so you can choose rather than have it chosen for you. Everything below is computable from data this app already plans to collect, now including the continuous WHOOP stream. Annotate any row you want in, or any row you want dropped, and it becomes part of the plan.

One honest framing first: this is n equals one, with autocorrelated time series and heavy confounding. That rules out deep learning entirely, and it rules out most of what people mean by "ML" here. What it does not rule out is a lot of genuinely useful statistics, provided every number ships with its own uncertainty. The methods that fit are rolling and robust regression, cross-correlation for lags, changepoint detection, state-space filtering, survival analysis, and Bayesian estimates that start from population priors and shrink toward your own data as it accumulates. That last one is what makes week 2 usable instead of useless.

How an insight reaches you

Each one is computed in lib/analytics/ as a pure function over logged data, never by the model, and written to derived_insights with its statement, its number, its n, and its confidence interval. Only insights past threshold enter the cached prompt prefix, so the generator reasons from your measured patterns rather than from generic guidance. The same rows render on the progress screen with their uncertainty visible.

If you want a starting set

My recommendation would be all eighteen tier 1 rows, since they are cheap and mostly prerequisites for the rest, plus five tier 2 rows chosen for decision value: your tendon load ceiling (35), the pain lag (36), which lifts correlate with your jump (29), prescription calibration (41), and the WHOOP recovery index (9). That set answers "how much jumping can I take", "what strength work is worth doing", "how ready am I today", and "is this app calibrated to me" - which is most of the value.

Nutrition, tied to the training phase

Logging

You type what you ate in plain words. The parser checks the foods cache first, so a repeated meal resolves to identical macros rather than being re-estimated slightly differently each time. Only genuinely new items hit the model.

Targets

Phase-aware. A surplus during accumulation. A cut permitted only when tendon sites are healthy and the current block is not a realization phase, because the ebook ties jumping to relative strength, which makes bodyweight a programming variable rather than a vanity metric.

Risks worth naming

WHOOP token and coverage gaps

Refreshing rotates the refresh token and invalidates the old access token, so the stored pair must be replaced atomically or the connection silently dies. Webhooks exist for sleep, recovery, and workouts only, so day strain and body measurements need a nightly poll. And WHOOP weight is a profile field, not a scale reading, so daily bodyweight stays manual.

Cold start on personalization

The memory layer has nothing to work with for the first several weeks. Early plans will be generic ebook-compliant programming. That is acceptable, but it should be stated in the UI so it does not read as the app being dumb.

Rule conflicts are possible

The rule of 60 percent, the volume distribution target, and the tendon hard block can jointly become unsatisfiable. The repair loop must therefore be allowed to fail loudly rather than spin, and the validator report has to name which rules conflicted.

Answered

The last three questions, now decided

Nothing is left open. Each answer has a design consequence, spelled out below so the build does not quietly reinterpret it later.

Planning horizon: roll forward weekly phase 5

The mesocycle is still declared up front, because the block-scope rules need it: its type, its 1 to 2 target abilities, its technical focus, and its stable exercise complex are fixed when the block opens. What is generated weekly is the microcycle inside that declaration: which sessions land on which days, and at what load.

That split is what makes weekly rolling safe rather than sloppy. Because the complex is already fixed, weekly generation cannot drift into a different program; it can only rearrange and re-load within the block. Two implementation consequences: the load-variation rule compares each new week against the weeks already generated in the block rather than seeing the whole block at once, and the rule of 60 percent is evaluated within the week being generated, which it already was. Regenerating a week after your schedule moves is a first-class action, not a workaround, and each regeneration is stored as its own proposal so the audit trail stays intact.

Exercise directory: broad stock seed, editable phase 2

Ships with a broad, fully attribute-tagged directory covering jump and plyometric work, lower body, and upper body, so the generator has real range from day one. Every exercise carries an availability flag, and the pre-filter removes anything unavailable before the prompt is built, so a stock entry you cannot do is simply invisible rather than something to reject later.

You can add, edit, disable, and re-tag entries from /library, including your own variants and coaching cues. The directory stays a closed set from the model's point of view: it selects from what exists and never invents an exercise. If it wants something absent, it files a suggested addition you can accept into the directory, which keeps the taxonomy clean while still letting the library grow from use.

Memory: auto-commit frequently, with a short exception list phase 7

Reflection commits inferred facts automatically after each logged session. Every fact stores its source as inferred, its confidence, and the observations behind it, and a new fact supersedes the old one rather than piling up, so the store stays a current picture instead of an archive. Anything you have stated directly outranks anything inferred and is never overwritten by it.

What makes aggressive auto-commit safe is reversibility rather than caution: a memory feed shows what was learned and when, every fact is one tap to correct or delete, and a correction immediately supersedes the inference. Two categories still require your confirmation, because a wrong inference there is expensive rather than merely annoying: anything that changes tendon behaviour, such as raising a contact ceiling or advancing a protocol phase, and anything that would retire an exercise or a movement class entirely. Everything else lands on its own.
